## F3-34 — Fix retour arrière WebView

**Story :** `docs/stories/phase-3/🔄-F3-34-fix-back-navigation-webview.md`
**Périmètre :** `apps/mobile/src/screens/ArticleScreen.tsx` uniquement
**Hors scope :** `WikipediaWebView.tsx` (inchangé), `game.store.ts` (inchangé)

### Diagnostic confirmé

`webViewRef.current?.goBack()` navigue dans l'historique interne de la WebView. Wikipedia mobile utilise des chaînes de redirections : chaque visite d'article génère plusieurs entrées dans cet historique (ex : `Article_A → redirect_canonical → Article_A`). Un seul appel `goBack()` remonte d'une entrée intermédiaire, pas vers l'article précédent visible. D'où les 3 appuis constatés.

La solution est un **stack applicatif de titres** géré par `ArticleScreen`. Le retour arrière met à jour `currentTitle` directement — la WebView recharge l'article précédent proprement via un changement de `source`.

#### 4. `handleGoBack` — nouveau handler

```typescript
  articleStack.current.pop();
```

### Architecture de la solution

**Principe :** toutes les paires sont préchargées dans `MultiplayerSetupScreen` au moment de la configuration. Elles sont stockées dans le store multijoueur (`allPairs`). `MultiplayerRoundTransitionScreen` lit la paire préchargée depuis le store au lieu de charger dynamiquement.

Ce changement élimine le temps de chargement entre les manches et garantit que le groupe a validé toutes les paires avant de commencer.

### 1. Nouveau hook `useRefreshablePair`

Créer `apps/mobile/src/hooks/useRefreshablePair.ts`.

Ce hook est distinct de `useRandomPair` car il expose `refresh()` sans remettre le state à `loading` au montage initial — le chargement est déclenché par le montage ET par chaque appel à `refresh()`. L'implémentation réutilise la même logique fetch que `useRandomPair` (AbortController, gestion 503, etc.).

```typescript
/**
 * useRefreshablePair — WikiHop Mobile — F3-32
 *
 * Hook similaire à useRandomPair mais avec support du rechargement manuel.
 * Chaque appel à refresh() déclenche un nouveau chargement de paire.
 * Contrairement à useRandomPair, ce hook est conçu pour une utilisation
 * dans des composants qui gèrent plusieurs paires indépendantes.
 *
 * Conventions :
 *   - Export nommé useRefreshablePair
 *   - AbortController + flag cancelled pour éviter setState après démontage
 *   - Même logique de fetch que useRandomPair (réutiliser la même URL et la même
 *     gestion d'erreur)
 */

import type { ArticleSummary } from '@wikihop/shared';
import { useCallback, useEffect, useState } from 'react';
import { useLanguageStore } from '../store/language.store';

export type RefreshablePairState =
  | { status: 'loading' }
  | { status: 'success'; start: ArticleSummary; target: ArticleSummary }
  | { status: 'error'; message: string };

export interface UseRefreshablePairReturn {
  state: RefreshablePairState;
  /** Recharge une nouvelle paire depuis le backend. Remet state à 'loading'. */
  refresh: () => void;
}

export function useRefreshablePair(): UseRefreshablePairReturn
```

**Implémentation :**
- `refreshKey` : state `number` initialisé à `0`
- `refresh()` : `setState({ status: 'loading' })` puis `setRefreshKey(k => k + 1)`
- `useEffect` sur `[language, refreshKey]` : déclenche le fetch à chaque changement
- Gestion identique à `useRandomPair` : AbortController, `cancelled` flag, gestion HTTP 503, gestion AbortError

**TDD strict :** `useRefreshablePair` est un hook custom — commit des tests AVANT l'implémentation.

Cas de test requis pour `useRefreshablePair` :
1. Au montage : state initial `'loading'`, puis `'success'` après fetch réussi
2. `refresh()` : remet le state à `'loading'` et relance le fetch
3. Deux appels `refresh()` rapides : seul le dernier fetch aboutit (AbortController annule le précédent)
4. Fetch retourne HTTP 503 : state `'error'` avec message "Service temporairement indisponible"
5. Fetch retourne autre erreur HTTP : state `'error'` avec message générique
6. Démontage pendant fetch : pas de setState (AbortError ignoré)

```typescript
 * Calcule le classement global sur l'ensemble des manches, avec rangs partagés.
 *
 * Critères de classement (identiques à rankPlayersGlobal) :
 *   1. Nombre de victoires (desc)
 *   2. Total de sauts sur les manches gagnées (asc)
 *   3. Durée totale sur les manches gagnées (asc)
 *   4. En cas d'égalité totale : ordre d'arrivée conservé (tri stable)
 *
 * Règle de rang partagé :
 *   - Deux joueurs avec wins, totalJumps et totalDurationMs identiques ont le même rang.
 *   - Le rang suivant tient compte du nombre de joueurs ex-aequo avant lui.
 *   - Ex. : 3 joueurs, les 2 premiers ex-aequo → ranks 1, 1, 3 (pas 1, 1, 2).
 *
 * TDD strict : tests avant implémentation.
 *
 * @param roundHistory - Tableau des manches (peut être vide : retourne tableau vide)
 * @param playerNames  - Noms des joueurs dans l'ordre de leur index
 */

  roundHistory: MultiplayerRoundResult[][],
  playerNames: string[],
): GlobalRankEntryWithRank[]
```

**Implémentation suggérée :**
1. Calculer les stats agrégées (même logique que `rankPlayersGlobal`)
2. Trier selon les mêmes critères
3. Parcourir le tableau trié et attribuer les rangs :

```typescript
// Attribution des rangs — parcours linéaire après tri
let currentRank = 1;
for (let i = 0; i < sorted.length; i++) {
  if (i === 0) {
    sorted[i].rank = 1;
  } else {
    const prev = sorted[i - 1];
    const curr = sorted[i];
    // Ex-aequo si les 3 critères de classement sont identiques
    const isEqual =
      curr.wins === prev.wins &&
      curr.totalJumps === prev.totalJumps &&
      curr.totalDurationMs === prev.totalDurationMs;
    if (isEqual) {
      curr.rank = prev.rank;
    } else {
      // Le rang tient compte du nombre de joueurs ex-aequo avant
      curr.rank = i + 1;
    }
  }
}
```

**Note :** `currentRank` déclaré ci-dessus est inutile — utiliser directement `i + 1` pour le rang non-ex-aequo.
